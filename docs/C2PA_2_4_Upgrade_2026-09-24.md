## Standard Versus Implementation

C2PA 2.4 includes AI disclosure, related-assertion references and revised action
validation, including `allActionsIncluded`. It also extends embedding formats.
These are specification capabilities, not automatic SDA features.
[C2PA 2.4 specification](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html).

| Area | SDA implementation in this candidate | Remaining boundary |
|---|---|---|
| Cryptographic verification | Delegated to pinned native SDK; validation codes retained | No independent full conformance certification |
| Presence, integrity, trust, declaration | Separate visible fields; provenance has no numeric probability | Trust snapshot is not yet approved or installed |
| Active and ingredient records | Reachable embedded history shown; bounded traversal; unresolved history noted | `history_complete` means display traversal completed, not complete or trusted life history |
| Actions | v1/v2, numeric assertion instances, wildcard/named defaults, explicit overrides | Unknown assertion versions do not create verdicts |
| Partial scope | Regions and related-action source declarations retained as context | No region-level visual overlay; scoped source declarations excluded from whole-file verdicts |
| History completeness | Show signer's `allActionsIncluded` value, including unknown | It is a declaration, not independent proof of exhaustive editing history |
| AI disclosure | Model type/name/identifier and human-oversight declaration displayed where present | Not scored; no inference of whole-file generation or scientific validity |
| Trust validation | Per-reader settings, integrity/trust separation, reviewed-policy gate | Real trusted, expired, revoked and timestamped chain matrix still required |
| Remote references | No manifest retrieval, OCSP fetch or permitted network hosts | No external-reference content validation, live revocation or soft-binding recovery |
| Exports | Full C2PA evidence retained in Markdown, CSV, PDF and PPTX | JSON remains the detailed machine-readable report; exports are not signed credentials |
| New formats | No new upload type enabled merely because SDK supports it | HTML, structured text credentials, live-stream and new container coverage need separate integration tests |

Native release notes also describe parser/security hardening and revised
validation rules. This update is not a substitute for a fresh dependency
advisory scan or testing every hostile-media path. Validation may differ from
older runs; never silently rewrite historical reports.

## Real Local Observations

The researcher-supplied Dreamina MP4 was read locally with both SDK versions.
Original bytes were unchanged, checked by SHA-256. No cloud inference or upload
was performed. Identifying film details and raw reports remain in private cache.

| Check | Old SDK | New SDK |
|---|---|---|
| Embedded active record and parent | Read successfully | Read successfully |
| Integrity state | Valid | Valid |
| Signer trust | Untrusted | Untrusted |
| Explicit AI source type / AI disclosure | Not present in either record | Not present in either record |
| Official-anchor diagnostic comparison | Still untrusted | Still untrusted |
| SDA provenance verdict | Inconclusive | Inconclusive, with fuller visible explanation |

The file declares a ByteDance signer, an active opening/transcoding record and a
Dreamina creation ingredient. This is useful evidence but not a trusted AI-origin
declaration. The newer SDK also reports skipped OCSP and additional BMFF hash
exclusions; the full codes are retained. "Integrity valid" refers to the SDK's
validation rules and covered bindings, not every byte being unconditionally signed.

The checked-in Firefly JPEG's in-memory tampered variant remains rejected by the
real SDK. Synthetic fixtures test the application policy; they are not substitutes
for production signed samples across all five platforms.

## Trust Review

An explicit utility downloads public official signer/TSA lists to a private review
folder, pins the source commit and records hashes, roles and certificate details.
The draft is **unapproved**; it neither installs roots nor changes runtime trust.
HTTPS delivery and a checksum are not independent verification of a signed list.

```bash
.venv/bin/python scripts/prepare_c2pa_trust_review.py
```

This command uses the network for public certificate lists only. It is not run by
the app. The inspector can compare an exact snapshot using `--review-anchors` and
`--review-sha256`; comparisons remain unapproved and cannot enable overrides.

Follow [C2PA_Trust_Policy.md](C2PA_Trust_Policy.md) for review and installation.
Do not add a film's own certificate to an allow-list to make it pass. Select trust
roots based on policy, not desired classification. Official and legacy ITL trust
must not be silently conflated. [Trust-list guidance](https://opensource.contentauthenticity.org/docs/conformance/trust-lists/).
