behind the combined assessment.

the research app uses your own provider accounts and API keys (BYOK).

## How the verdict works

SDA Vision combines model assessments, Content Credentials and supporting
file checks through a defined set of decision rules. Each result records
the findings, coverage and reasoning behind the verdict.

- **Content Credentials provide evidence of declared origin.** A C2PA
  declaration of AI-generated or AI-composited content takes precedence
  when validation is complete and integrity and signer trust meet the
  configured policy. Missing credentials leave origin unresolved by
  this check.

- **Vision assessments use corroboration between models.** At least two
  matching, eligible model votes are required for a model-based verdict.
  Each vote must meet the verdict-and-rating rules. Where the available
  assessments do not meet these rules, the result is Inconclusive.
  Statistical independence between models is not assumed.

- **Uncertainty remains visible.** An Inconclusive model reply contributes
  no directional vote, whatever its rating. Ratings remain available for
  comparison and are not calibrated probabilities. See the
  [26 September method record](docs/Method_Change_Record_2026-09-26.md).

- **Local forensics adds supporting observations.** File-level findings
  can corroborate model assessments and help guide further review.
  They cannot determine the verdict on their own.

- **Video and document results retain their individual findings.**
  Sampled frames or pages appear alongside the combined assessment and
  an indicative summary rating. A mixture of likely authentic and
  synthetic findings produces an Inconclusive combined verdict,
  directing attention to the individual results.

- **Watermark coverage depends on the available service.** The current
  release has no configured automatic watermark detector. Manual
  external checks and pasted Second Opinion replies provide additional
  context outside the combined score.

Reports organise the findings under “Evidence supporting this verdict”
and “Additional findings”. “Context for this result” explains individual
checks, while “How this assessment was reached” records the decision
steps. Timestamped summaries support reporting and citation.

| Provider | Type | Signal |

## Run it

```bash
./run.sh
```

The command launches the installed app using its existing backend and
frontend build. By default, it runs on localhost, selects an available
port starting at 8100, and prints the address to open. You can also
double-click `boot-vision.command` to launch it in the same way.
Installation and frontend rebuilding are handled separately through
`setup.sh`.

On a new machine, run `./setup.sh` once (native Python 3.12 is the tested runtime,
Node 20.19+ on 20.x or Node 22.12+, and internet access; Apple Silicon macOS is the
tested platform).
It creates `.venv`, installs hash-locked Python dependencies, uses `npm ci`, builds the frontend
and creates `.env` if missing. Add approved API keys to `.env`, then use
`./run.sh`. Every provider is optional. After editing frontend source, explicitly
run `./setup.sh --build-only` before launch. Complete setup before the presentation so the installed build is ready to launch.

**PowerPoint slide previews:** install LibreOffice separately on the backend computer to preview uploaded `.pptx` decks. The public demo uses prepared slides. See [PowerPoint preview setup](docs/PowerPoint_Preview_Setup.md) for installation, controls and preview scope.

For the versioned software/archive preparation work, see
[`release/README.md`](release/README.md) for the current preparation pack and
[`release/RELEASE_NOTES.md`](release/RELEASE_NOTES.md) for changes and remaining checks.

For updated provider IDs and exact `.env` instructions, see
[`docs/Provider_Upgrade_2026-09-24.md`](docs/Provider_Upgrade_2026-09-24.md).
For new OpenAI/Google examples, see
[`docs/Example_Pack_Replacement.md`](docs/Example_Pack_Replacement.md).

C2PA runs offline and reports integrity and declared provenance. Provenance
overrides additionally require a reviewed local trust snapshot; see
[the trust policy](docs/C2PA_Trust_Policy.md). Watermark checks follow the
manual workflow described above. The C2PA 2.4-targeted candidate uses Python
SDK 0.37.12 / native 0.91.0; validator certification has not been established. See the
[upgrade and limitations](docs/C2PA_2_4_Upgrade_2026-09-24.md) and
[ByteDance, Adobe, Runway, Midjourney and LinkedIn scope](docs/Platform_Provenance_Scope_2026-09-24.md).

## Multimodal input

| Input | Handling |
|---|---|
| Image | analysed directly |
| PDF | `PDF_MODE=auto` extracts embedded figures, falling back to page rendering; C2PA on the original |
| PPTX | embedded slide images; text-only analysis when no visual frames are extracted, explicitly noted in the report |
| Video | frames sampled across the timeline (ffmpeg); per-frame verdicts |
| Transcript (txt/srt/vtt/md) | text content-analysis pass |
| Audio (m4a/mp3/wav) | transcoded + transcribed (Gemini-native, Whisper fallback), then analysed as text |

Video uploads also receive local soundtrack inspection. Optional Google audio-content
assessment and Suno credentials checks each require separate explicit consent and
are recorded alongside the visual verdict, outside its score. See [Soundtrack workflow](docs/Audio_Workflow_2026-09-24.md)
for coverage, external data flows and limitations. AI-origin detection from the sound itself is outside this workflow.

## Local research features

Set `DEV_MODE=true` in `.env` on your own access-controlled machine to enable:

- **Local corpus browser** for picking research files.
- **Saved runs** - every analysis is written to `dev_runs/` (with a perceptual
  hash per frame) so results accumulate for the next phase of analysis.
- **Batch upload** - select up to 5 files at once; each is analysed and saved.
- **Symbolic-diffusion graph** - `scripts/build_diffusion_graph.py` turns the
  accumulated `dev_runs/` (or a corpus subset) into a GEXF graph for Gephi, where
  perceptual-hash similarity groups visually related items for further investigation.
  Distribution history: not assessed. The public demo provides a prepared graph
  of its example set; local corpus analysis belongs to the research app.

## Stack

- Backend: FastAPI (Python). All detection logic is here and framework-agnostic.
- Frontend: React + TypeScript (Vite), in `frontend/`. Self-contained; designed
  with clean component boundaries so it can later be adapted as a plugin.

## Data protection and privacy

The local research app uses your own API accounts and keys
(bring-your-own-key, or BYOK). It reads keys from the process environment
or `.env` to authenticate requests to configured providers. The supplied
`.gitignore` excludes `.env` files and saved research runs.

Media preparation and local checks run on your machine. Enabled external
analyses send the relevant media, excerpts or text to the selected
providers, under their account terms and data-handling policies.
The app does not collect usage telemetry.

Processing uses memory and, for some media and export operations,
temporary local files. These files are removed after normal processing;
interrupted processing may leave files requiring cleanup.

**Recorded-demo external checks:** SynthID Detector and the OpenAI image checker
appear side by side, each with a visible results box. Return from the service
and paste its complete reply into **SynthID results** or **OpenAI results**.
The demo offers prepared examples only, with page or slide images for document
checks. Its OpenAI shortcut is enabled for image examples. Replies stay in the
browser session, separately from the recorded findings and model scores.
Download session notes before changing example or reloading. The dedicated
SynthID Detector replaces the former Gemini chat shortcut in this demo.

Google or OpenAI receives the file or image you choose on its service, including
retained metadata, under that service's account, current terms and any charges,
separately from SDA's API accounts. Opening a link sends no media.

The separate research app retains its detailed external-check form, including
file identity, date, reported scope and outcome. A manually pasted reply is not
an independently verified service response. See [workflow and scope](docs/External_Watermark_Checks.md)
and [participant instructions](docs/Participant_External_Checks.md).

### Planning your research use

- **Code and media permissions:** the MIT licence applies to the project's
  code. Media and datasets have their own permissions and terms.
  Data-protection obligations apply to your use of personal data.

- **Institutional and provider roles:** identify the controller and
  processor roles for your actual research workflow with your
  institution's Data Protection Officer (DPO). Review the data flows
  and security arrangements before moving to shared hosting.

- **Personal and sensitive information:** media and transcripts may
  identify people or reveal information about their health, political
  opinions or religious beliefs. Apply your institution's
  data-protection policy to this material, including publicly
  available sources.

- **Assessment and approvals:** work with your institution and DPO to
  establish the appropriate lawful basis, safeguards and scope of any
  Data Protection Impact Assessment (DPIA). Complete a DPIA where
  required and review it when the processing changes.

- **Saved research records:** with `DEV_MODE=true`, analyses are saved
  unencrypted in `dev_runs/`, including reports, thumbnails, filenames
  and extracted text where available. Use this mode on your own
  access-controlled machine. Keep these records local and delete them
  according to your project's retention schedule. The Public preview
  toggle leaves this storage setting unchanged.

See [`PRIVACY.md`](PRIVACY.md) for the detailed data flows, storage
behaviour and information supporting institutional review.
